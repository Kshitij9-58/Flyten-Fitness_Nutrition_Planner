# Flyten

A nutrition and training planner. Enter your age, height, weight, activity level and
goal, and it returns a daily calorie target, a macro split, a day of meals, a
seven-day training week, a twelve-week weight projection, and a session tracker.

**Live:** [flyten-fitness-nutrition-planner.vercel.app](https://flyten-fitness-nutrition-planner.vercel.app)
· **API:** [/health](https://flyten-fitness-nutrition-planner.onrender.com/health)

No account required. Sign-up exists, but the calculator works fully without one.

---

## The interesting part: measuring a RAG pipeline and deleting it

This project began as a "RAG-grounded AI coach" over a 15.7 MB, 80,000-row
fitness dataset, with a retrieval stack of BM25, dense embeddings, reciprocal
rank fusion and a reranker.

Before shipping it, I measured what the corpus actually contained. Across the 16
combinations of (gender, goal, BMI category) the dataset produced:

- **4 distinct meal plans**
- **4 distinct exercise schedules**
- **BMI category alone determined the output.** Gender and goal were decorative.

Worse, the mapping was unsafe. A user selecting fat loss whose BMI computed as
underweight was served a high-calorie bulking plan, because BMI was the only
input that mattered.

So the 80,000 rows were collapsed offline into `plan_table.json`: 16 entries,
5 KB, generated by `build_plan_table.py`. The CSV no longer ships or gets parsed
at boot. Retrieval was replaced with a dictionary lookup, which is faster,
deterministic, testable, and removed the entire CUDA dependency stack from the
deployed image. Build time on Render went from over five minutes to under one.

`retrieval.py` is kept in the repo. The implementation is sound and I would use
it again, but it has no corpus worth retrieving over, so it is not wired into
the API. Keeping unused machinery in the hot path to make an architecture
diagram look impressive is how systems rot.

## How the numbers are calculated

**Resting burn** uses the Mifflin-St Jeor equation, multiplied by an activity
factor between 1.2 and 1.725 to give daily expenditure, then adjusted roughly
500 kcal below for fat loss or 300 above for muscle gain.

**Protein** is set between 1.8 and 2.2 g per kg of bodyweight, highest in a
deficit, since protein is what protects lean mass when calories are low. Fat is
held near 25 percent of calories and carbohydrate takes the remainder.

**The burn calculator** ("what does it actually cost to eat?") uses
`kcal/min = (MET - 1) × 3.5 × kg / 200`. The minus one matters: one MET is
resting metabolism by definition, and counting it as exercise is the standard
error in these calculators. Including it made every session look about 13
percent cheaper than it was. Interval activities carry no average speed, because
the rest between reps is most of the session.

**The twelve-week projection** uses roughly 7700 kcal per kg of bodyweight. It
is drawn as a straight line with the caveat stated underneath, because real
rates slow as bodyweight falls and water shifts hide progress week to week. A
projection with no caveat sets people up to feel like failures in week three.

## Safety behaviour

These are deliberate and worth keeping:

- If BMI is underweight **and** the goal is fat loss, the plan is built for
  maintenance instead, with a warning pointing to a doctor or registered
  dietitian. The plan reports the goal it actually applied, not the one that was
  requested, so the explanatory copy can never contradict the numbers on screen.
- The burn calculator always ends with "none of this is a reason to skip the
  food." Food-to-exercise converters tip into guilt-driven eating easily.
- Both beginner guides explain reps, sets, push days and hand-measure portions
  in plain language. A plan written in gym shorthand is unusable by the person
  who most needs the structure.
- A plan owned by an account answers **404** rather than 403 to a stranger, so
  the response cannot be used to confirm that a plan exists at a given id.

## API

| Method | Path | Auth | Purpose |
|---|---|---|---|
| GET | `/health` | none | Coach provider, plan table size, auth state, db dialect |
| POST | `/generate/` | optional | Build a plan |
| GET | `/api/profile/{id}` | optional | Load a plan, owner-only if owned |
| GET | `/api/my-plans` | required | List the account's plans |
| PATCH | `/api/profile/{id}/progress` | optional | Tick off training days |
| PATCH | `/api/profile/{id}/claim` | required | Attach an anonymous plan to an account |
| POST | `/api/chat` | optional | Coach grounded in the user's own plan |

`/health` reports the live database dialect, so a misconfigured deploy shows up
there rather than silently losing data until someone notices.

## Running locally

Two terminals.

**Backend:**
```bash
cd backend
python -m venv venv
venv\Scripts\Activate.ps1          # macOS/Linux: source venv/bin/activate
pip install -r requirements.txt
set FLYTEN_COACH_PROVIDER=none     # macOS/Linux: export
uvicorn app.main:app --reload
```

**Frontend:**
```bash
cd frontend
npm install
npm run dev
```

With no Supabase variables set, auth is simply off and every endpoint works
anonymously. With no `DATABASE_URL`, it falls back to a local SQLite file.

### Configuration

**Backend:** `SUPABASE_URL`, `SUPABASE_JWT_SECRET`, `FLYTEN_ALLOWED_ORIGINS`,
`FLYTEN_COACH_PROVIDER`, `DATABASE_URL`

**Frontend:** `VITE_API_URL`, `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`

## Design

The interface is built around sprint vocabulary rather than the ring-and-ECG
language every fitness app reaches for. The hero carries a real 100 m velocity
profile, steep through 30 m, maximum velocity around 50 to 60 m, slight decay to
the line. Energy sits on a single marked axis with ticks every 500 kcal, so the
size of a deficit reads as visible distance rather than three numbers to compare
mentally. Macros run as lanes against a shared calorie scale. The training week
is set as a start list, with the plan reference sized like a bib number.

## Known limitations

Stated plainly rather than hidden, because they are the next pieces of work:

- **Plans do not survive deploys in production.** `DATABASE_URL` is not yet set,
  so the deployed backend writes to SQLite on an ephemeral disk. Migrating to
  Postgres is the top item.
- **The coach endpoint has no caller.** `coach.py` works and is grounded in the
  user's own plan, but no UI calls `/api/chat`. It will either get a real
  interface or be removed. A chat box added purely to justify the endpoint would
  not be worth shipping.
- **Vegetarian reference guidance is empty** across all 16 plan table entries,
  because the source dataset had no vegetarian dimension. The app discloses this
  gap in a warning rather than inventing content.
- **Minimum age is 13**, while the calorie floors and deficits applied are adult
  ones. This should be raised, or forced to maintenance for minors.
- Account hardening, including email verification and non-sequential plan
  identifiers, is in progress.
